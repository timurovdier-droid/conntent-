# Техническая спецификация — ContentPilot AI

**Версия:** 1.0  
**Дата:** 21 октября 2026 г.  
**Основание:** PRD ContentPilot AI v0.1 + уточнение: база знаний, деплой на Vercel, база данных Turso.  
**Статус:** Спецификация для реализации MVP; решения, которые пока не утверждены, помечены как открытые.

---

## 1. Цель и границы системы

ContentPilot AI — адаптивное веб-приложение для создания, редактирования и хранения маркетингового контента с помощью Gemini. Пользователь задаёт параметры задачи, а агент использует профиль бренда, историю текущего проекта и релевантные материалы из базы знаний пользователя.

### Цели MVP

1. Создать текстовый контент на русском и узбекском языках.
2. Редактировать результат командами на естественном языке, сохраняя историю версий.
3. Создавать изображения для контентных материалов.
4. Поддерживать пользовательскую базу знаний, чтобы агент опирался на документы и заметки вместо выдумывания фактов.
5. Хранить данные в Turso и разворачивать приложение на Vercel.
6. Контролировать доступ к данным, расход API и ошибки генерации.

### Не входит в MVP

- Автоматическая публикация в социальные сети.
- Генерация видео и озвучки.
- Парсинг произвольных сайтов по URL как источник базы знаний.
- Командные роли и сложное согласование контента.
- Собственная языковая модель, fine-tuning и автономные действия во внешних сервисах.
- Тарифы и биллинг пользователей, кроме внутренних квот и учёта использования.

## 2. Зафиксированный технологический стек

| Слой | Решение | Примечание |
|---|---|---|
| Frontend и серверные маршруты | Next.js App Router + TypeScript | UI, серверные обработчики и серверные функции в одном приложении |
| Стили | Tailwind CSS; компонентная система на выбор команды | Компоненты должны быть доступными с клавиатуры и адаптивными |
| Хостинг приложения | Vercel | Preview-развёртывания для веток и Production для основной ветки |
| Основная БД | Turso Cloud, SQLite-compatible | Все SQL-запросы выполняются только на сервере |
| Векторный поиск | Встроенные vector-функции/index в Turso/libSQL | Используется для поиска фрагментов базы знаний по embeddings |
| AI-текст и агент | Gemini API через серверный AI-адаптер | Model ID задаётся через конфигурацию, не вшивается в UI |
| Генерация изображений | Отдельный image-generation путь через Gemini | Отдельные лимиты и события использования |
| Файлы | Vercel Blob в приватном режиме — рекомендуемый вариант | Если Blob не подключён, исходные файлы не сохранять: хранить извлечённый текст и метаданные |
| Аутентификация | Провайдер должен поддерживать Next.js App Router и Turso | Конкретную библиотеку выбрать до начала auth-реализации |
| Валидация | Схемы на сервере, например Zod | Все внешние входы и ответы модели валидируются |

### Правила архитектуры

- Не обращаться к Turso или Gemini напрямую из браузера.
- API-ключи и токены доступны только серверному runtime.
- Доступ к любому ресурсу проверяется на сервере по `user_id` и/или `workspace_id` при каждом запросе.
- Взаимодействие с моделью и БД вынести за интерфейсы-адаптеры, чтобы можно было заменить модель или SDK без переписывания UI.
- Миграции БД хранить в репозитории и запускать контролируемо; не создавать таблицы автоматически при каждом запросе.
- Для Vercel Preview и Production использовать отдельные базы/учётные данные Turso, чтобы тестовые данные не попадали в рабочую базу.

## 3. Архитектура приложения

```text
Браузер
  └── Next.js UI (Vercel)
       └── Server Actions / Route Handlers
            ├── Auth + проверка доступа
            ├── Content Service
            │    ├── Brand Context
            │    ├── Knowledge Retrieval (RAG)
            │    ├── Gemini Text/Agent Adapter
            │    └── Version + Usage Service
            ├── Image Service → Gemini Image API
            ├── Knowledge Ingestion Service
            │    ├── извлечение текста из файла
            │    ├── разбиение на фрагменты
            │    ├── Embedding Adapter
            │    └── запись фрагментов и векторов в Turso
            └── Repository Layer → Turso

Файлы-источники → приватное файловое хранилище (опционально Vercel Blob)
```

### Основные модули

- **Auth:** регистрация, вход, выход, восстановление доступа, текущая сессия.
- **Workspace/Brand:** рабочее пространство и редактируемый профиль бренда.
- **Content:** генерация, редактирование, варианты, проекты и версии.
- **Knowledge Base:** документы, заметки, обработка, индексирование, поиск и удаление.
- **Assets:** изображения, статусы генерации, скачивание.
- **Usage:** квоты, события использования модели, расчёт ориентировочной стоимости.
- **Admin/Observability:** минимальные системные показатели, ошибки и квоты; без неограниченного просмотра приватного содержимого пользователей.

## 4. База знаний и RAG

### 4.1 Назначение

База знаний хранит факты и материалы бренда: описания товаров/услуг, правила коммуникации, часто задаваемые вопросы, условия, утверждённые преимущества и другую информацию, на которую AI должен опираться при создании контента.

### 4.2 Источники в MVP

- Загрузка PDF, DOCX, TXT и Markdown.
- Вставка текста вручную с названием источника.
- Управление списком источников: просмотр статуса, повторная обработка и удаление.
- Импорт страниц по URL — вне MVP.

**Стартовые ограничения, требующие проверки на выбранном тарифе Vercel:** максимальный размер файла 10 MB; поддерживаемые форматы показываются в интерфейсе. Лимит должен быть конфигурируемым.

### 4.3 Жизненный цикл документа

1. Пользователь выбирает рабочее пространство и загружает файл либо вставляет текст.
2. Сервер проверяет сессию, владельца workspace, расширение, MIME type и размер.
3. Создаётся запись документа со статусом `queued` или `processing`.
4. Сервер извлекает текст и, если формат поддерживается, сохраняет метаданные страниц/разделов.
5. Нормализованный текст разбивается на перекрывающиеся фрагменты. Начальная настройка — около 700–1 000 токенов на фрагмент и перекрытие около 100 токенов; это параметры конфигурации, которые уточняются по тестам.
6. Для каждого фрагмента генерируется embedding отдельной embedding-моделью.
7. Текст, позиция и вектор сохраняются в Turso. Для векторного столбца фиксируются размерность и идентификатор embedding-модели.
8. Документ получает статус `ready`; при ошибке — `failed` с безопасным сообщением и возможностью повторить обработку.
9. При удалении документа удаляются связанные chunks/embeddings и оригинальный файл, если он хранится отдельно.

### 4.4 Поиск релевантных фрагментов

- При генерации агент получает вопрос/тему и параметры контента, затем создаёт embedding поискового запроса.
- Поиск ограничивается текущим `workspace_id`; фрагменты других пользователей недоступны даже при совпадении векторов.
- Возвращаются наиболее релевантные фрагменты, стартовый ориентир — top 5, с ограничением общего объёма контекста.
- При наличии большого числа документов можно добавить фильтр по выбранным источникам.
- В запрос к основной модели передаётся только необходимая выдержка из источников, а не вся база знаний.
- Если релевантных фрагментов нет, агент продолжает работу по профилю бренда и данным задачи; система не должна добавлять выдуманные факты.
- В интерфейсе показывается блок «Использованные источники» с названием документа и фрагментом/страницей, если доступно.
- Если утверждение не поддерживается источниками или данными пользователя, AI должен отметить его как требующее проверки или использовать плейсхолдер.

### 4.5 Защита от prompt injection

Содержимое файлов и фрагментов является недоверенными данными, а не системными инструкциями. Текст из базы знаний не может переопределить правила безопасности, раскрыть секреты или заставить агента обращаться к инструментам вне разрешённого набора. Загрузка документа не даёт ему прав выполнять действия.

### 4.6 Индексация и изменение embedding-модели

- В таблице фрагментов хранить `embedding_model` и версию/идентификатор пайплайна индексации.
- Для одного векторного столбца размерность должна соответствовать выбранной embedding-модели. Перед внедрением нужно подтвердить модель, размерность и доступность в целевом API.
- Смена модели требует переиндексации; смешивать в одном индексе векторы с несовместимой размерностью запрещено.
- Повторная обработка должна быть идемпотентной: не создавать дубликаты chunks при повторном запуске одной операции.

## 5. Пользовательские сценарии

### 5.1 Первый запуск

1. Пользователь регистрируется или входит.
2. Создаёт workspace и профиль бренда (может пропустить необязательные поля).
3. Может добавить документы в базу знаний.
4. Нажимает «Создать контент» и выбирает формат, цель, канал, язык и тему.
5. Система использует профиль бренда, настройки задачи и релевантные фрагменты базы знаний.
6. Результат открывается в редакторе; пользователь может отредактировать, сохранить, скопировать или экспортировать его.

### 5.2 Редактирование результата

1. Пользователь открывает проект.
2. Вводит команду, например: «Сократи текст вдвое, сохрани факты и не используй эмодзи».
3. Backend проверяет доступ, читает текущую версию и ограничения задачи.
4. Агент возвращает структурированный результат; новая версия сохраняется отдельно.
5. Исходная версия остаётся доступной для восстановления.

### 5.3 Создание визуала

1. Пользователь выбирает «Создать изображение».
2. Сервер формирует image prompt с учётом темы, бренда и выбранного формата.
3. Показывается статус `processing`, затем `ready` или `failed`.
4. Успешное изображение привязывается к проекту, учитывается в usage и доступно для скачивания.

### 5.4 Работа с базой знаний

1. Пользователь открывает раздел «База знаний».
2. Загружает файл или вставляет текст.
3. Видит статус обработки и ошибку, если обработка не удалась.
4. После статуса `ready` источник доступен агенту в последующих генерациях этого workspace.
5. Пользователь удаляет источник; его текст, embeddings и связанный файл удаляются согласно политике хранения.

## 7. API-контракт

Все пути ниже предполагают префикс `/api`. Имена могут корректироваться при реализации, но функциональность и авторизация обязательны.

### 7.1 Контент и проекты

| Метод и путь | Назначение | Основные входные данные |
|---|---|---|
| `GET /api/me` | Текущий пользователь и workspace | Текущая сессия |
| `GET /api/projects` | Список проектов пользователя | `page`, `limit`, `query` |
| `POST /api/projects` | Создать проект | `title`, `contentType`, `platform` |
| `GET /api/projects/:id` | Проект и его версии | `id` + проверка доступа |
| `PATCH /api/projects/:id` | Переименовать/изменить метаданные | Поля для изменения |
| `DELETE /api/projects/:id` | Удалить проект и его ресурсы | `id` + проверка доступа |
| `POST /api/content/generate` | Создать первую версию контента | `projectId`, `contentType`, `goal`, `platform`, `language`, `topic`, `tone?`, `constraints?`, `useKnowledgeBase?` |
| `POST /api/projects/:id/edit` | Создать следующую версию по команде | `baseVersionId`, `instruction` |
| `POST /api/projects/:id/variants` | Создать 2–3 варианта | `baseVersionId` или параметры задачи |
| `GET /api/usage` | Текущие квоты и история usage | Период/пагинация |

### 7.2 База знаний

| Метод и путь | Назначение | Основные входные данные |
|---|---|---|
| `GET /api/knowledge/documents` | Список источников текущего workspace | `status?`, `page?` |
| `POST /api/knowledge/documents` | Создать источник из файла/текста | `file` либо `title` + `text` |
| `GET /api/knowledge/documents/:id` | Статус и метаданные источника | `id` + проверка доступа |
| `POST /api/knowledge/documents/:id/reindex` | Повторная обработка | `id` + проверка доступа |
| `DELETE /api/knowledge/documents/:id` | Удалить источник и данные индекса | `id` + проверка доступа |
| `POST /api/knowledge/search` | Поиск для отладки/интерфейса | `query`, `limit?`; только в границах workspace |

`POST /api/knowledge/search` может оставаться внутренним интерфейсом, если отдельный поиск пользователю в MVP не нужен. Retrieval во время генерации должен вызываться непосредственно из серверного `Content Service`, а не через HTTP-запрос к самому себе.

### 7.3 Изображения и системные статусы

| Метод и путь | Назначение |
|---|---|
| `POST /api/projects/:id/assets` | Запустить генерацию визуала |
| `GET /api/assets/:id` | Получить статус и метаданные собственного файла |
| `GET /api/health` | Проверить доступность приложения без вывода секретов |

### 7.4 Формат ошибки

```json
{
  "error": {
    "code": "AI_PROVIDER_UNAVAILABLE",
    "message": "Не удалось создать результат. Попробуйте ещё раз позже.",
    "requestId": "<request-id>",
    "retryable": true
  }
}
```

- `message` безопасен для пользователя и не раскрывает ключи, SQL, stack trace или внутренний prompt.
- `requestId` позволяет найти техническую запись в логах.
- Повтор операции не должен автоматически списывать квоту повторно, если запрос не создал успешный результат; спорные случаи фиксируются отдельно.

## 8. Контракт AI-агента

### 8.1 Вход генерации

```json
{
  "contentType": "social_post",
  "platform": "instagram",
  "goal": "leads",
  "language": "ru",
  "topic": "описание услуги",
  "tone": "дружелюбный, уверенный",
  "constraints": ["не выдумывать цены", "без эмодзи"],
  "useKnowledgeBase": true
}
```

Это пример контракта, а не жёсткое ограничение списка платформ/целей. Backend валидирует типы, длины полей и допустимые значения.

### 8.2 Структура результата

Структура зависит от типа контента, но базовый объект должен включать:

```json
{
  "title": "...",
  "hook": "...",
  "body": "...",
  "cta": "...",
  "hashtags": [],
  "visualPrompt": "...",
  "notesToVerify": [],
  "language": "ru",
  "format": "social_post",
  "variantLabel": "Основной вариант",
  "usedSources": [
    { "documentId": "...", "title": "...", "chunkId": "...", "page": null }
  ]
}
```

После ответа модели сервер проверяет схему. `usedSources` формируется или верифицируется сервером из реальных retrieved chunks; модель не должна сама придумывать идентификаторы, ссылки или страницы источников.

### 8.3 Последовательность генерации

1. Проверить сессию, доступ к workspace/project и квоту.
2. Валидировать параметры запроса.
3. Загрузить профиль бренда и данные проекта.
4. При `useKnowledgeBase=true` получить релевантные chunks текущего workspace.
5. Сформировать серверный prompt с разделёнными зонами инструкций и недоверенного контекста.
6. Вызвать настроенную текстовую модель.
7. Проверить структуру и ограничения результата.
8. Сохранить `ContentVersion` и `UsageEvent` в Turso.
9. Вернуть результат и фактический список источников.

### 8.4 Редактирование

Редактирование должно сохранять исходные факты, запреты, язык и формат, кроме случаев, когда пользователь явно просит изменить конкретный параметр. Каждая успешная правка создаёт новую версию с `parent_version_id` и кратким описанием команды пользователя.

### 8.5 Модели

В PRD указаны Gemini 3.8 Flash для текстового агента и Gemini Nano Banana 2.1 для изображений. Эти значения следует хранить в переменных окружения и повторно проверить доступность, model ID, цены, квоты и условия обработки данных перед production. Для embeddings требуется отдельная модель; её ID и размерность фиксируются после проверки и оценки качества на русских и узбекских материалах.

## 9. Схема данных Turso

Все таблицы должны использовать идентификаторы UUID/ULID в виде `TEXT`, timestamps в UTC и параметризованные запросы. JSON-поля допустимо хранить как сериализованный JSON-текст, если нет необходимости в отдельных нормализованных таблицах.

### Индексы и ограничения

- Индексы на `workspaces.owner_id`, `brand_profiles.workspace_id`, `projects.workspace_id`, `content_versions.project_id`, `knowledge_documents.workspace_id`, `knowledge_chunks.workspace_id`, `knowledge_chunks.document_id`, `usage_events.user_id/created_at`.
- `content_versions.parent_version_id` ссылается на предшествующую версию; удаление проекта каскадно удаляет версии и связи с assets.
- У каждого `knowledge_chunks` хранить отдельный `workspace_id` для явной фильтрации tenant-данных, но согласованность с родительским документом обязательно проверять сервером/ограничениями.
- Векторный индекс создаётся только после утверждения embedding-модели и размерности. Векторный столбец в Turso/libSQL использует фиксированную размерность; пример документации — `F32_BLOB(D)` и индекс `libsql_vector_idx(...)`.
- Применять внешние ключи там, где они поддерживаются выбранной конфигурацией и включены для соединений; критические проверки доступа всё равно выполняются в сервисном слое.

## 10. Работа с файлами

- Разрешённые форматы для MVP: PDF, DOCX, TXT, MD.
- Проверять размер и тип фактического содержимого, а не только имя файла или `Content-Type` браузера.
- Не исполнять загруженные файлы и не считать содержимое файла инструкциями для backend.
- Для исходных файлов использовать приватное хранилище и временные подписанные URL. Если приватное хранилище не настроено, после извлечения текста исходный файл не сохраняется.
- Не передавать постоянные публичные URL на пользовательские документы в ответах API.
- Для PDF сохранять номер страницы, если библиотека извлечения это позволяет. Для DOCX/MD/TXT допустимо хранить позицию/порядок фрагмента без номера страницы.
- Любой процесс извлечения должен иметь timeout и обрабатывать пустые/повреждённые документы.

## 11. Безопасность и приватность

1. Проверять сессию на каждом защищённом route/action.
2. Проверять ownership ресурса на сервере; знание ID чужого проекта не даёт доступа.
3. Хранить секреты только в переменных окружения/secret store Vercel; секреты не должны иметь префикс `NEXT_PUBLIC_`.
4. Применять rate limit отдельно к генерации текста, изображениям, загрузке документов и входу.
5. Ставить лимиты на размер входного текста, число chunks, число вариантов и частоту повторов.
6. Санитизировать HTML/Markdown при показе; исходные документы не отображать как исполняемый HTML.
7. В логах хранить `requestId`, тип операции, модель, статус, задержку и расход. Не логировать полный prompt или содержимое документов без крайней необходимости.
8. Не раскрывать system prompt, credentials, пользовательские данные или содержимое чужого workspace.
9. Удаление документа удаляет chunks и embeddings, а также оригинал из storage, если он там есть. Полное удаление аккаунта включает связанные проекты, assets, KB-источники и usage-данные согласно опубликованной политике хранения.
10. Перед production подготовить Terms of Service, Privacy Policy, допустимое использование и сроки удаления/очистки резервных копий.

## 12. Производительность и отказоустойчивость

- Целевой ориентир PRD: обычный текстовый черновик менее чем за 30 секунд; фактические P50/P95 измеряются на пилоте.
- Таймауты и повторы задаются отдельно для текстовой модели, изображения, извлечения текста и embeddings.
- Повторять только временные ошибки, с небольшим числом попыток и backoff; запрещены бесконечные циклы.
- Использовать idempotency key для дорогих операций, если пользователь может повторно нажать кнопку или клиент повторяет запрос.
- Для долгих операций KB/image использовать статусную модель `queued → processing → ready/failed`. Если фоновые задачи ещё не подключены, MVP может обрабатывать малые файлы в запросе, но должен иметь строгие лимиты и понятные ошибки; долгие/большие файлы следует вынести в очередь на следующем этапе.
- Ошибка Gemini не должна удалять ранее сохранённый контент или историю.
- База знаний не обязательна для каждой генерации: недоступность retrieval не должна приводить к молчаливому использованию недостоверных источников; интерфейс сообщает, что база знаний временно не использована.

## 13. Развёртывание: Vercel + Turso

### 13.1 Git-процесс

- Репозиторий Git является источником кода.
- Pull request/ветка создаёт Vercel Preview Deployment.
- Основная ветка (например, `main`) используется для Production Deployment.
- Перед переводом в Production проходят тесты, миграции и smoke-check.
- Для Preview использовать отдельную базу Turso и отдельные секреты от Production.

### 13.2 Переменные окружения

| Переменная | Где использовать | Назначение |
|---|---|---|
| `TURSO_DATABASE_URL` | Server only | URL рабочей/preview базы |
| `TURSO_AUTH_TOKEN` | Server only | Токен доступа к Turso |
| `GEMINI_API_KEY` | Server only | Доступ к Gemini API |
| `GEMINI_TEXT_MODEL` | Server only | Model ID текстового агента |
| `GEMINI_IMAGE_MODEL` | Server only | Model ID генерации изображений |
| `GEMINI_EMBEDDING_MODEL` | Server only | Model ID генерации embeddings |
| `AUTH_SECRET` | Server only | Секрет выбранного auth-провайдера, если нужен |
| `NEXT_PUBLIC_APP_URL` | Client/server | Публичный адрес приложения, не секрет |
| `BLOB_READ_WRITE_TOKEN` | Server only, optional | Токен приватного файлового хранилища Vercel Blob |

Секреты не включать в git, клиентскую сборку, логи или публичные ошибки. После изменения env на Vercel требуется новый deploy, чтобы изменения действовали в новой сборке.

### 13.3 База данных и миграции

- Создать отдельные Turso database instances для production и preview/development, если это соответствует бюджету и плану.
- Миграции нумеруются, хранятся в каталоге `db/migrations/` и запускаются из контролируемой команды/CI перед выкладкой совместимой версии приложения.
- Для рискованных изменений применять expand-migrate-contract: сначала совместимые новые столбцы/таблицы, затем перенос данных, потом удаление старой структуры отдельным релизом.
- Сделать процедуру резервного копирования/восстановления и периодически проверять её.
- Перед релизом проверить актуальные ограничения Turso, выбранного JS/TS SDK, Vercel runtime и лимиты функций.

### 13.4 Порядок первого деплоя

1. Создать Git-репозиторий и проект Next.js.
2. Создать проект Vercel и подключить репозиторий.
3. Создать production и preview базы Turso.
4. Добавить env-переменные отдельно для Preview и Production.
5. Запустить миграции и seed для development/preview.
6. Выполнить тестовую генерацию текста, загрузку документа, retrieval и удаление документа.
7. Проверить, что секреты отсутствуют в client bundle и сетевых ответах браузера.
8. Выполнить Production Deployment и smoke-test основных сценариев.
9. Настроить домен, мониторинг ошибок, уведомления о расходах и лимитах.

## 15. Тестирование

### Автоматические тесты

- Unit-тесты chunking, валидации ответов AI, нормализации текста и расчёта квот.
- Integration-тесты репозиториев Turso, миграций, CRUD для проектов и базы знаний.
- API-тесты проверки прав доступа и форматов ошибок.
- E2E-тесты регистрации → профиль бренда → генерация → редактирование → сохранение → экспорт.
- E2E-тест базы знаний: загрузить документ → проверить `ready` → сгенерировать контент с найденным фактом → удалить источник → убедиться, что chunks и storage-объект удалены.
- Негативный тест: пользователь A не может читать документ/проект пользователя B, даже подставив известный ID.
- Негативный тест: prompt injection в документе не меняет системные правила и не запускает инструменты.
- Проверка, что API keys не попадают в JS bundle, source maps, client logs или ответы API.

### Набор оценки модели

Подготовить минимум 30–50 задач на русском и узбекском: посты, объявления, описания товаров, Reels-сценарии, переводы и редакторские команды. Для базы знаний отдельно тестировать релевантность найденных chunks, точность ссылок на источники, отсутствие неподтверждённых фактов и корректное поведение при отсутствии подходящих фрагментов.

### Definition of Done для MVP

- Все Must-требования из раздела 6 проходят тесты.
- Пользователь может выполнить основной сценарий без ручного вмешательства разработчика.
- Все AI-вызовы и ошибки учитываются в usage.
- Preview и Production развернуты отдельно; секреты разделены.
- Есть понятная политика удаления документов и проектов.
- Smoke-тест после deployment проходит успешно.

## 16. План реализации

1. **Основа:** Next.js, Turso, миграции, auth, workspace, профиль бренда.
2. **Текстовый агент:** адаптер Gemini, схемы ответа, шаблоны, генерация и редактирование.
3. **Проекты и версии:** сохранение, восстановление, копирование и экспорт.
4. **База знаний:** загрузка файлов/текста, extraction, chunking, embeddings, векторный индекс, retrieval и источники в UI.
5. **Изображения:** генерация, статус, storage и скачивание.
6. **Безопасность и наблюдаемость:** ограничения частоты/квоты, permissions, логи, удаление данных.
7. **Deploy и закрытый пилот:** preview, production, smoke-check, тестирование с реальными пользователями.

Зависимости: реализацию RAG нельзя считать завершённой, пока не зафиксированы embedding-модель, её размерность и поддерживаемый векторный тип/индекс в целевой конфигурации Turso.

## 17. Открытые решения до начала реализации

| Вопрос | Рекомендуемое решение по умолчанию | Почему нужно подтвердить |
|---|---|---|
| Auth-провайдер | Выбрать один совместимый с Next.js App Router и Turso | Влияет на сессии, восстановление доступа и схему users |
| Файловое хранилище | Приватный Vercel Blob; fallback — хранить только извлечённый текст | Оригиналы файлов не стоит складывать в реляционную БД |
| Максимальный размер файла | Начать с 10 MB и скорректировать после проверки лимитов | Ограничения зависят от способа upload, runtime и тарифа |
| Embedding-модель | Выбрать после проверки размерности, цены и качества ru/uz | Векторный столбец требует фиксированной размерности |
| Модели Gemini | ID брать из конфигурации и проверить перед production | Модели, квоты и стоимость изменяются |
| Фоновые задания | Для прототипа — ограниченная обработка; для больших файлов — очередь | Длительные операции не должны зависеть от одного HTTP-запроса |
| Регион Turso/Vercel | Выбрать после проверки доступности и задержки | Нужны реальные измерения и требования к обработке данных |
| Квоты | Установить после измерения стоимости типовых операций | Не фиксировать бесплатные лимиты без проверки расходов |
| Тарифы | Не блокируют MVP | Нужны только после определения бизнес-модели |
